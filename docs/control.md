# 控制：算法、状态机与整定

本文说明**这台风扇是怎么被控的**，以及每个数字是怎么来的。
每个数字都注明了它的来历：**实测的**、**按器件标称值入场的**、或是**整定选出来的**。
三者的可信程度不同，混用会让整套参数失去可追溯性，所以文中分开写。

---

## 1. 为什么是级联，而不是「温度直接算占空比」

```
温度 ──►[ 分段曲线 + 迟滞 ]──► 目标转速 ──►[ PI ]──► 占空比 ──► 风扇
              (外环)                        (内环)      │
                                                        │
              实测转速 ◄──────── FG 捕获 ◄──────────────┘
```

两个理由：

**① 对象是非线性的。** 占空比→转速的关系在低压区有一段**行为未定义**的死区
（4 线风扇规范：<20% 由厂商自定；本工程实测 0% 时风扇仍维持约 295 rpm 不停转）。
把温度直接映射成占空比，等于把这段非线性塞进外环，整定会随工作点漂移。
闭到转速上之后，**内环把非线性吃掉了**，外环看到的对象始终大致线性。

**② 对扰动免疫。** 电源电压波动、进风口被挡、滤网积灰，都会改变
「同样的占空比能吹出多少风」。闭到转速上，这些扰动由内环吸收。

### 级联带来的两个「免疫」

| 按标称值入场的量 | 影响 | 为什么不影响控制正确性 |
|---|---|---|
| **rpm 绝对倍率**（每转脉冲数可能是 2 以外的值） | 屏上的数字不是铭牌转速 | 曲线纵轴与内环的实测值**同单位**（都来自 `fan_control_rpm_from_period_us`），倍率误差在闭环内被消掉 |
| **NTC 参数**（R25 / B / 分压电阻取该型模块的标称值） | 温度的绝对刻度随之平移，曲线**横轴**跟着移动 | 偏移量在运行期可调（串口 `TEMP`、按键），现场把工作点挪到合适的位置即可；要做绝对刻度就按 §5.2 做两点校准 |

## 2. 外环：分段曲线 + 迟滞

### 为什么是分段线性插值，不是阶梯查表

阶梯查表会让目标转速**阶跃**：温度跨过一格，目标突然跳一档，内环立刻去追这个
阶跃，屏上的 rpm 会一跳一跳。线性插值让目标随温度连续变化；迟滞只负责挡住
「在某个点附近来回抖」，正好是它该干的活、不多不少。

### 迟滞做在温度上，不做在转速上

被控量是温度，抖动也来自温度（ADC 噪声、环境扰动）。把迟滞定义成「温度得挪开
1 ℃ 才认」比「转速得差 200 才认」更贴近物理，而且与曲线斜率无关——曲线陡的地方
不会因此变得迟钝。

迟滞带的**中心**是「当前输出对应的温度」，不是曲线的某个锚点：这样换挡点跟着
工作点走，而不是把温度硬拽到锚点上。

### 曲线锚点（`app/app_control.c`）

| 温度 | 目标转速（观测单位） |
|---|---|
| 28.0 ℃ | 0（不转） |
| 30.0 ℃ | 3500（直接跳到最小可控转速，见下） |
| 35.0 ℃ | 5000 |
| 40.0 ℃ | 6500 |
| 45.0 ℃ | 8000 |
| 50.0 ℃ | 9500 |
| 55.0 ℃ | 11500 |
| 60.0 ℃ | 13500 |
| 70.0 ℃ | 16456（实测 100% 时的观测转速） |

> **纵轴低端为什么从 3500 起步、而不是 0→1200→2200 那样连续爬升**：
> 4 线风扇 <20% 占空比行为未定义，而 20% 对应约 3450 观测 rpm，
> 所以实际能用的转速只有 `{0} ∪ [≈3450, 满速]`。曲线低端若画在中间那一段，
> 得到的目标是**够不到的**（2026-10-11 上板实测暴露：目标 619 rpm，
> 而风扇最慢就是 3450）。详见下面 §3「目标转速也要夹进可达区间」。

> **横轴（温度）按 NTC 的标称参数换算**，纵轴是板上实测的观测转速。
> 改这张表不影响任何算法，也不需要动别的地方。

## 3. 内环：PI（没有 D 项）

### 为什么没有 D

依据 Microchip **AN3530《PID Fan Speed Control for 4-Wire Fans》**：风扇是单向
驱动的一阶对象（加速靠电机、减速靠惯性与风阻），微分项没有实际收益；
更要紧的是，转速由 **FG 捕获的周期**换算而来，低速时周期只有几十微秒、量化台阶
明显，D 项会把这点量化噪声放大成控制量的抖动（风扇会听见「滋滋」的调节声）。

**这是有意省略，不是漏了。** 若确实要用，应在调用处先对测量值做低通。

### 抗积分饱和

积分饱和是 PI 最经典的事故：输出被限幅顶住时误差仍在把积分器往上推，等目标
降下来，积分器要花很久才退回去——表现为「该降的时候降不下来」。

本工程用**条件积分**：输出已经顶在上下限、且误差还在往同方向推时，这一拍不累加
积分。另加一道保险：积分器本身也夹在输出范围内。

**为什么不开输出速率限制**（`pi_control` 有这个能力，这里设成 0）：曲线上的迟滞
已经把目标转速的变化限制在每 1 ℃ 几百 rpm 之内，输出不会阶跃；切模式的冲击由
`pi_reset()` 的无扰切换负责。而速率限制在**抗饱和判断之后**才施加，长期生效会让
积分器悄悄卷绕——没有实际收益却引入风险，所以关掉。

### 无扰切换

切进 AUTO 时用**当前实际占空比** `pi_reset()` 把积分器预置到对应值，
于是「切模式」不会让扇叶抽一下。

### 占空比下限下沉到 PI 的输出范围

4 线风扇在 <20% 的行为未定义，所以输出只允许是 `{0} ∪ [20, 100]`。

关键点：**下限必须交给 PI 自己**，不能只在最后夹一下。若 PI 被允许输出 17%、
外层再把它抬到 20%，风扇就转得比 PI 以为的快；PI 于是把输出压向 0，风扇停；
转速掉下来，PI 又把它抬上去——**极限环**，现象是转速周期性地上蹿下跳。

把下限放进 PI 的输出范围后，它就会老实饱和在 20% 上不动，并触发
`RPM_NOT_TRACKING` 报警，如实报告「够不到目标」。

**目标转速为 0 时绕开 PI**（直接输出 0）：否则 PI 会带着 20% 的下限去追一个 0
的目标，把风扇顶在最低速上转，与「停机」自相矛盾。

### 目标转速也要夹进可达区间

同一件事的另一半：曲线的**目标转速**也必须落在
`{0} ∪ [最小可达转速, 满速]` 里——最小可达转速就是 20% 对应的约 3450 rpm。

这是上板实测暴露的（2026-10-11）：曲线低端给出 619 rpm 这样的目标，
而风扇最慢就是 3450，于是目标永远够不到、PI 长期贴在饱和边界上。
现象上风扇转得没错（本来就该是 20%），但屏上与遥测里的「目标 vs 实测」
变成一对永远够不着的数，`RPM_NOT_TRACKING` 的语义也说不清。

`thermal_control` 里做了这道夹取，所以**任何**曲线都不会漏——
不必指望每条曲线都画得恰好。

## 4. PI 增益：IMC（λ）整定

```
Kp = τ / (K · λ)          Ki = 1 / (K · λ)          Ti = τ
```

其中 λ 是整定旋钮（期望的闭环时间常数）。不用 Ziegler-Nichols——它给的是
「四分之一衰减」的激进整定，风扇这种**会被耳朵听见**的对象不该用激进整定。

### 4.1 先说一个真实事故：按假定值整定，上板即振荡

第一版按**假定** τ = 0.3 s 整定，发布 `Kp = 0.0037`、`Ki = 0.0123`。
上板（AUTO 模式，目标 6005 rpm）立刻**持续振荡**：

```
duty  31 → 22 → 20 → 21 → 20 → 22 → 25 → 28 → 33 → 39 → 46 → 54 → 61 → 68 → 74 → 74 → 69 …
rpm  9724 → 9442 → 8655 → 7865 → 6996 → 6191 → 5471 → 4830 → 4274 → 3751 → 3346 → 2954 → …
```

幅度 ±3500 rpm、周期约 4.5 s 的**极限环**（不是测量噪声——手动模式下同一个
转速读数稳在 ±50 rpm 以内）。

**根因很清楚：** 原来的 `Ti = Kp/Ki = 0.30 s`，**恰好等于那个错的假设 τ**；
而真实 τ 是 1.4 s。**积分时间比对象还快近 5 倍**，是教科书级的积分致振。

### 4.2 实测辨识（2026-10-11）

方法就是下面 5.1 里写的那套，数据：

| 项 | 结果 |
|---|---|
| 20% 稳态 | 3324 rpm（模型 3450，差 4%） |
| 60% 稳态 | ~10060 rpm（模型 9970，差 1%）→ **静态模型 K ≈ 163 rpm/% 可信** |
| 阶跃 20%→60% | 3324 → 10010 用了约 2.6 s，**起步有一段约 0.3 s 的平坦**（静摩擦 + 内部限速） |
| **τ** | **≈ 1.4 s** |
| 等效死区 | ≈ 0.3 s 可见，但见下面的说明 |

> ⚠️ **「等效死区」在仿真里取 0.8 s，比肉眼可见的 0.3 s 大。**
> 理由是标定出来的：只给 0.3 s 时，第一版增益在仿真里是「稳定」的，
> 而板子上在振——说明真实环路的滞后比纯延时更多（FG 量测通路、EMA、
> 风扇内部的二阶动态都被这个参数一并吸收）。把死区调到 0.8 s，
> 仿真才复现出板上的极限环。**测试的价值就在这条区分度上。**
> 这两个仿真参数固化在 `tests/test_pi_control.c` 与 `tests/test_thermal_control.c` 里。

### 4.3 重新整定后的发布值

积分时间钉死在**实测的 τ** 上（IMC 的规矩就是 `Ti = τ`），再用 λ 留裕度：

```
τ ≈ 1.4 s、K ≈ 163 rpm/%、λ = 2.5 s（= 1.8 τ）

Kp = τ/(K·λ) = 1.4/(163 × 2.5) ≈ 0.0034
Ki = 1/(K·λ) = 1/(163 × 2.5)   ≈ 0.0025      →  Ti = Kp/Ki ≈ 1.4 s = τ ✓
```

> **λ 的单位是「秒」**（不是 τ 的倍数），下表四行同样按秒代入。核对方法：
> 用发布值反解 `λ = τ/(K·Kp) = 1.4/(163 × 0.0034) ≈ 2.5 s`，与取值一致；
> 若误按 `λ = 2.5τ = 3.5 s` 去算，得到的是 0.0025，与发布值对不上——
> 这一步最容易把 τ 的数值 1.4 多乘一次。

**上板复测**（AUTO，目标 5208 rpm）：收敛，稳态 5142~5282（±1.5%，
即 1% 占空比量化台阶 163 rpm），无振荡。

λ 从 1 s 扫到 3 s 的取舍见下表（仿真，死区 0.8 s；λ 与 τ 之比一并列出）：

| λ | λ/τ | Kp | Ki | 超调 | 稳定时间 | 死区到 1.6 s 时 |
|---|---|---|---|---|---|---|
| 1.0 s | 0.7 | 0.0086 | 0.0061 | 76% | 12.8 s | **振荡** |
| 1.5 s | 1.1 | 0.0057 | 0.0041 | 48% | 9.2 s | 105% 超调 |
| **2.5 s** | **1.8** | **0.0034** | **0.0025** | **21%** | **8.4 s** | 54% 超调 |
| 3.0 s | 2.1 | 0.0029 | 0.0020 | 14% | 9.0 s | 41% 超调 |

取 λ = 2.5 s 是因为辨识本身有误差，而 1.5 s 在死区稍大时就退化了。

> **这道 λ 扫描是有回归护栏的**：`tests/test_pi_control.c` 里有一条用例专门
> 断言「第一版的 0.0037 / 0.0123 必须在同一个仿真里振起来」，另一条断言发布值
> 收敛。只测「新增益稳定」是不够的——那样任何人把仿真参数调松，结论照样通过。

> ⚠️ **换风扇、改风道都要重新测 τ 与死区后重算，不要照抄这几个数。**

## 5. 标定

三个量决定了这套系统的物理刻度：**机电时间常数 τ**（决定 PI 整定）、
**NTC 的温度刻度**、**rpm 的绝对倍率**。三者都能用现有遥测与串口命令现场标定，
不需要示波器或额外的仪器。

### 5.1 机电时间常数 τ —— 板上阶跃辨识

**结果：τ ≈ 1.4 s，静态增益 K ≈ 163 rpm/%**（方法与原始数据见 §4.2），
内环 PI 的增益就是据此整定的。

换风扇、改风道后重测的流程：

1. `MODE MANUAL` + `MANUAL 20`，等它稳下来，记 rpm 基线；
2. 改成 `MANUAL 60`，打一个 **+40% 的阶跃**；
3. 同时开 `STREAM 1` 记录 `@TEL` 帧，直到转速稳定；
4. **τ ≈ 达到 63% 阶跃幅值所需的时间**；
5. 按 §4.3 的公式重算 Kp、Ki，用 `PID <kp> <ki>` 在线验证，再写回代码。

把 rpm(t) 导出来画图（`tools/plot_telemetry.py`）就是一条标准的阶跃响应曲线——
这本身就是一份**系统辨识**记录。

### 5.2 NTC 两点校准 —— 决定曲线横轴的绝对刻度

温度这条链出厂用的是该型模块的标称参数（R25 = 10 kΩ、B = 3950、分压电阻 10 kΩ）。
要得到绝对刻度，做一次两点校准即可：取两个已知温度点（室温 + 冰水）各记录一次
原始 `raw`，由分压公式反解出两点的 R_NTC，再用 Beta 方程联立解出 R0 与 B。
完整推导写在 [`module/temperature/temperature.h`](../module/temperature/temperature.h) 顶部。

界面与遥测里的 `!CAL` 报警位就是这件事的**状态指示**：出厂即亮，校准完成后熄灭。
它的存在是有意的——让读数里那个「按标称参数换算」的事实始终可见，
而不是让一组标称值悄悄冒充实测值。

### 5.3 rpm 绝对倍率 —— 决定曲线纵轴的物理刻度

换算按 FG 每转 2 个脉冲（Intel 规范值）与「每个边沿只捕获一次」这两个约定。
要和风扇铭牌对齐，把屏上读数与铭牌比一下；若差一个**固定倍数**，两种可能：
每转脉冲数不是 2（改 `FAN_CONTROL_PULSES_PER_REV`），或 FG 边沿有振铃被重复
捕获（开 TIM2 输入滤波器 + 在 PA1 与 3V3 之间加 4.7 kΩ 外部上拉）。

标定之后，曲线纵轴与 `FAN_CONTROL_RPM_PER_PERCENT` / `_INTERCEPT`
**要按同一倍率一起缩放**——它们必须始终同单位，否则前馈与闭环会各说各话。

## 6. 状态机

```
        ┌──────┐  首拍接管
        │ INIT │──────────────┐
        └──────┘              ▼
                        ┌─────────┐  温度或转速失效   ┌──────────┐
              ┌────────►│  AUTO   │◄─────────────────►│ DEGRADED │
              │         └─────────┘   恢复后自动回      └────┬─────┘
              │              │                              │
      K1长按循环│        用户切换(受 500 ms 最小驻留约束)      │ 两者同时失效
              │              ▼                              ▼
        ┌─────┴────┐   ┌──────────┐                  ┌──────────┐
        │  MANUAL  │◄──┤   OFF    │                  │  FAULT   │
        └──────────┘   └──────────┘                  └────┬─────┘
                                                          │ K2 长按 RESET
                                                          └──► AUTO
```

| 模式 | 占空比 | 报警灯 | 蜂鸣器 | 说明 |
|---|---|---|---|---|
| INIT | 0 | 灭 | 灭 | 上电到接管之间 |
| OFF | 0 | 灭 | 灭 | ⚠️ **怠速**：0% 时风扇仍约 295 rpm，不是真停 |
| MANUAL | 手动档位 | 灭 | 灭 | 忽略传感器做控制，但仍如实上报报警 |
| AUTO | 控制器输出 | 灭 | 灭 | 级联控制 |
| DEGRADED | 安全兜底值 | 灭 | 静音 | 传感器失效但还能凑合运行 |
| FAULT | **100%** | **亮** | **响** | 冷却系统失效安全 = 满速；需 RESET |

### 几个刻意的决定

- **FAULT 是粘性的**：一旦进入就只认 RESET，不会因为传感器「某一拍看着还行」就
  自己跳出去。冷却系统反复在正常与故障之间抖动，比稳定停在故障态更危险。
- **报警灯亮在 FAULT，而不是过温**：报警器件的语义是「这台冷却系统出问题了」，
  而不是「现在热」——热本身由转速去响应。**冷却风机故障时应满速，绝不能断电。**
- **降级用非对称去抖**：进兜底要连续 3 拍无效，退出要连续 5 拍有效。单次 glitch
  （例如开关继电器时的电源毛刺）不该让风扇抽一下。
- **手动档不受传感器失效影响**：用户已经接管了输出，此时改策略只会让人困惑；
  但报警照报。
- **最小驻留 500 ms** 只约束**用户切换**（AUTO↔MANUAL↔OFF）；降级与 FAULT 是
  安全动作，立即生效。
- **FAULT 下 K1 一律被忽略**：「按几下就退出故障」不是一个安全的设计。

### 降级路径

| 失效 | 行为 |
|---|---|
| 温度读不到（AUTO 中） | 目标锁定兜底转速（8000 观测 rpm，安全偏高速），冻结积分。**读不到温度不能停** |
| 转速读不到（FG 线断） | 内环失去反馈 → 切**开环前馈**：按曲线目标经经验模型反算占空比。温度传感器还好好的，风扇仍随温度变化，只是精度差些 |
| 两者同时失效 | → FAULT：满速 + 报警灯 + 蜂鸣器 |
| OLED 不在 | 只是显示降级，**不影响控制**；报警位 `!OLED` 经串口照常上报 |

## 7. 时间基准

| 环节 | 周期 |
|---|---|
| 内环 PI + 温度/转速采样 + 状态机 | 100 ms |
| 遥测帧 / OLED 刷新 | 200 ms |
| 按键消抖采样 | 1 ms（SysTick 中断，与主循环阻塞无关） |

**dt 用真实 tick 差，并且夹上限。** 主循环里 OLED 刷新要搬 1 KB 软件 I2C
（几十毫秒），控制节拍**必然**有抖动；用真实 dt 之后抖动被自动补偿。夹上限
（标称周期的 10 倍）是为了挡住极端情况：若主循环被阻塞了一整秒，一拍吃进 1 s
的积分量会让输出直接甩出去。

**OLED 放任务表最后**，它的阻塞只挤占空闲时间，不会挤掉同一次循环里的控制与
遥测；且内容不变时跳过整屏刷新。

## 8. 验证纪律

| 层 | 手段 |
|---|---|
| 算法正确性 | `tests/` 下的宿主机单测（含一阶对象闭环仿真、极限环、抗饱和） |
| 配置被接受 | `tools/cubemx_apply.py roundtrip`（本项目**不新增外设**，通常用不到） |
| 取值合法 | CubeMX 日志里的 `Parameter (X) has invalid value` |
| **硬件行为** | 上板实测：捏住 NTC 看转速是否单调上升、拔掉 NTC 看是否进 DEGRADED、再拔 FG 看是否进 FAULT（报警灯亮 + 蜂鸣器响）、发 `MANUAL 50` 看转速跟随。**清单以 README 的「上板验收清单」为准**（那里有六条，逐条写明预期现象；报警灯/蜂鸣器的动作都在第 5、6 条里） |

**前三层不能替代第四层。** 「命令返回 OK」「编译通过」「单测全绿」都证明不了
风扇真的按你设计的路径转了。
