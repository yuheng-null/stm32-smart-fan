# smart_fan — 智能温控风扇系统

基于 STM32F407VET6 的温控风扇。

**控制结构是级联的**：温度经分段曲线（带迟滞）得到目标转速，内环 PI 再用 FG
实测转速把占空比调到那个目标上。这么做的理由、以及每个参数的来历，
都写在 [`docs/control.md`](docs/control.md)。

当前进度：**平台与外设全部实测通过**（时钟 168 MHz、串口中断收发、OLED / NTC /
按键 / 风扇 PWM + FG 测速 / 继电器 / 蜂鸣器）；**温控业务层已完成**——
级联控制、运行模式状态机、传感器降级与失效安全、串口命令协议与遥测帧、
OLED 视图，业务逻辑全部在 `module/` 下且为**纯计算**，
用宿主机单元测试覆盖（见下面的「测试」）。

> ⚠️ **两处尚未标定**，都已在代码与文档里显式标注、并在界面上以报警位提示：
> NTC 的两点校准、rpm 的绝对倍率。测量方法见
> [`docs/control.md`](docs/control.md) 的「待标定」。
> （风扇的机电时间常数 τ 已于 2026-10-11 实测，PI 增益据此整定。）

## 功能与现象

### 一句话说明它做了什么

**让风扇的转速跟着温度走；并且在传感器坏掉、或者追不上目标的时候，不出危险
——该转的时候不停，该报警的时候不沉默。**

具体包含五块：

| # | 功能 | 在哪 |
|---|---|---|
| 1 | 温控闭环：温度采样 → 分段曲线（带迟滞）→ 目标转速 → 内环 PI → PWM 占空比 | `module/thermal_control` |
| 2 | 六种运行模式与切换（按键 + 串口），含传感器失效降级与失效安全 | `module/fan_fsm` |
| 3 | OLED 实时显示（大字号温度 + 模式 + 目标/实测转速 + 报警码） | `module/display_view` + `app/app_display.c` |
| 4 | 串口行命令协议 + 结构化遥测帧（可导出画图调参） | `module/console` + `module/telemetry` |
| 5 | 全部业务逻辑为纯计算，可在 PC 上单测（9 个测试目标） | `tests/` |

### 上电后的头几秒，你会看到什么

| 时刻 | 现象 |
|---|---|
| 约 0.5 s | 串口打出中文开机横幅 + `SYSCLK = 168000000 Hz`（**这行是时钟树的独立验证**：主频错则波特率错，整屏乱码，你根本读不到它） |
| 约 0.5 s | `I2C scan: 1 device(s) 0x3C` → `OLED: OK`，屏上出现内容 |
| 之后每 200 ms | 串口一行遥测；屏同步刷新（**内容不变时跳过刷屏**，这是省掉 1 KB 软件 I2C 传输的手段） |
| 若室温 < 28 ℃ | 风扇**不转**（`duty 0%`）；OLED 大字号显示温度，右上角 `AUTO` |
| 若刚烧录/复位过 | 会看到 `rpm` 从一个几千的值一路滑到 0 —— 那是复位瞬间 PA8 浮空把风扇甩到全速后的**惯性滑停**，属正常 |

上电后 `alarms` 恒为 `0x08`（`!CAL`）—— 见下面的报警表，这是**有意常亮**的。

### 一、六种运行模式：每一种的现象

模式会同时反映在 **风扇转速 / 报警灯 / 蜂鸣器 / OLED / 串口** 五处。

| 模式 | 怎么进入 | 风扇 | 报警灯 | 蜂鸣器 | OLED 右上角 | 串口 `mode` |
|---|---|---|---|---|---|---|
| `INIT` | 上电瞬间 | 停（占空比 0） | 灭 | 静音 | `INIT` | 0 |
| `OFF` | K1 长按循环到它 / `MODE OFF` | **怠速**：占空比 0，实测仍有约 190~295 rpm 的余转，**不是真停** | 灭 | 静音 | `OFF` | 1 |
| `MANUAL` | K1 长按循环 / `MODE MANUAL` | 按手动档位转（K1/K2 加减） | 灭 | 静音 | `MANUAL` | 2 |
| `AUTO` | 上电默认 / `MODE AUTO` | 按温度曲线自动调速 | 灭 | 静音 | `AUTO` | 3 |
| `DEGRADED` | 传感器失效时**自动**进入 | 维持**安全偏高速**（不停） | 灭 | 静音 | `DEGR` | 4 |
| `FAULT` | 温度与转速**同时**失效 | **满速 100%** | **亮** | **响**（可静音） | `FAULT` | 5 |

`INIT` 只存在约 100 ms（第一拍控制就接管），正常情况下看不到。

**为什么报警灯亮在 `FAULT` 而不在「过温」**：报警器件的语义是「这套冷却系统出
问题了」，而不是「现在热」—— 热本身由转速去响应。**冷却风机故障时应满速，
绝不能断电**，所以继电器驱动的是报警灯，不是风扇供电。

### 二、按键操作与现象

| 操作 | 在 `AUTO` 下 | 在 `MANUAL` 下 | 在 `FAULT` 下 |
|---|---|---|---|
| **K1 短按** | 目标温度 **+0.5 ℃**（风扇起步更晚、更暖） | 占空比 **+10%** | 忽略 |
| **K2 短按** | 目标温度 **−0.5 ℃**（更凉） | 占空比 **−10%** | 忽略 |
| **K1 长按**（≥0.8 s） | → `MANUAL`（并用当前转速播种档位，不会一进手动就停） | → `OFF` | 忽略 |
| **K2 长按**（≥0.8 s） | 蜂鸣器**静音开关** | 同上 | **复位**：清报警回 `AUTO` |

几条刻意的约束：

- **模式最小驻留 500 ms**：连按不会让模式来回闪。降级与 `FAULT` 是安全动作，
  不受这条约束，立即生效。
- **`FAULT` 下 K1 一律被忽略**：「按几下就退出故障」不是一个安全的设计。
- **手动档位只允许 0 或 ≥20%**（4 线风扇 <20% 行为未定义）。从 20% 再往下按
  会直接落到 0（停），不会停在 10% 这种未定义档。
- 按键消抖在 **SysTick 1 ms 中断**里做，与主循环阻塞无关 —— 刷屏期间按键也不会漏。

### 三、串口命令与现象

行协议：一行一条，`\r` / `\n` / `\r\n` 都算结束，大小写不敏感。
**每条命令都会回 `@ACK,<命令>,OK` 或 `@ACK,<命令>,ERR,<码>`**
（这是把「命令发出去了」和「命令生效了」分开的手段）。

| 命令 | 现象 |
|---|---|
| `?` | 打印命令表 |
| `STATUS` | 先打一行人类可读状态，再打一行链路诊断 `link: rx_drop=N rx_err=N \| Tset=... manual=...%`，最后 `@ACK,STATUS,OK` |
| `MODE OFF\|AUTO\|MANUAL` | 模式按上表切换；受 500 ms 最小驻留约束，太快会被拒（回 `ERR`） |
| `MANUAL <0..100>` | 设手动档位。**1~19 会被抬到 20**（避开未定义区），0 允许（停机） |
| `TEMP <摄氏度>` | 设目标温度，如 `TEMP 32.5`。这是**绝对温度**，内部换算成相对曲线起步点的偏移；偏移被夹在 −10 ~ +15 ℃ 内 |
| `PID <kp> <ki>` | 在线整定内环。**只改增益，不重置积分器**——所以调参过程是连续的，不是每次都重启 |
| `STREAM <0\|1>` | `0` 人类可读行 / `1` CSV 遥测帧（切到 1 时先发一行 `#` 开头的表头） |
| `RESET` | 清报警并回 `AUTO`；**传感器没修好会立刻被打回 `FAULT`**——这是对的 |

### 四、报警位：每一位是什么意思、什么时候亮

串口遥测的 `alarms` 是一个位图的十六进制值；OLED 最后一行用短码显示当前置位的那些。

| 位 | 短码 | 含义 | 什么时候出现 | 现象 |
|---|---|---|---|---|
| `0x01` | `!TEMP` | 温度读数无效 | 连续 3 拍（300 ms）读不到有效温度 | 进 `DEGRADED`，风扇维持安全转速不停 |
| `0x02` | `!TACH` | FG 测速无信号 | **要求它转**（目标 > 0）却连续 3 拍没有有效转速 | 进 `DEGRADED`，内环切开环前馈 |
| `0x04` | `!TRACK` | 内环长时间追不上目标 | 偏差持续 >20% 达 3 s | 只报警，不改策略 |
| `0x08` | `!CAL` | **NTC 参数未标定** | **上电即常亮**，直到做两点校准 | 温度绝对值不可信，只看趋势 |
| `0x10` | `!OLED` | 屏幕不在 | 开机探测不到 0x3C/0x3D | 仅显示降级，**不影响控制** |

> `!TACH` 有一条容易搞反的规则：**风扇被命令停转时，FG 没有沿是预期行为，
> 不算故障**。否则冷天风扇停着，系统会一直挂着假故障（这是本项目上板实测
> 抓到的第一个 bug）。

### 五、典型场景的完整时间线

**场景 A：室温低于曲线起点（日常待机）**

```
温度 26 ℃ < 曲线起点 28 ℃
  → 目标转速 0 → 占空比 0%
  → 风扇不转（余转滑停到 0）
  → 模式 AUTO，alarms = 0x08（只有 !CAL）
  → OLED：大字号 26.0 / 右上角 AUTO / Tset 28.0 / duty 0% rpm 0 / tgt 0 e 0
```

**场景 B：温度升到曲线区间（正常控温）—— ✅ 已实测**

```
温度越 29.0 ℃（= 起步点 28.0 + 迟滞 1.0）那一刻，目标转速换挡到低位
  → 目标可选区间下限是 20% 占空比对应的约 3450 rpm
  → 内环 PI 把实测转速拉到目标上
  → 实测：目标 5254 时，稳态 5194~5344（±1.5%，即 1% 占空比的量化台阶）
  → 模式 AUTO，无新增报警
```

**场景 C：温度在换挡点附近小幅抖动**

```
迟滞带 ±1.0 ℃ 内来回 → **目标转速一动不动**
（若去掉迟滞，目标会跟着 ADC 噪声抖，转速跟着喘）
```

**场景 D：温度读数失效（拔掉 NTC）—— ❌ 未在真板子上验证**

```
连续 3 拍读不到有效温度（300 ms 去抖）
  → 目标锁定「兜底转速」8000 rpm（安全偏高速），冻结积分
  → 模式 AUTO → DEGRADED，alarms 增加 0x01
  → 现象：风扇**维持转速不停**，OLED 出现 !TEMP，串口 mode 变 4
插回 NTC 后连续 5 拍有效（500 ms）
  → 自动回 AUTO，!TEMP 消失
```

> 这条只验证到「逻辑正确」（单测覆盖 + 代码逐段核对）。**真板子上拔掉之后
> AO 悬空读到什么值没人测过** —— STM32 模拟输入悬空时读数不确定，若落在量程内
> 就不会触发兜底。详见下面验收清单里对「未验证」的说明。

**场景 E：FG 测速线断（风扇在转但读不到转速）—— ❌ 未验证**

```
要求它转（目标 > 0）却连续 3 拍没有有效转速
  → 内环失去反馈 → 切开环前馈：按曲线目标经经验模型反算占空比
  → 模式 DEGRADED，alarms 增加 0x02
  → 现象：风扇仍随温度变化，只是精度差些（温度传感器还好好的）
```

**场景 F：温度与转速同时失效 —— ❌ 未验证**

```
两者都失效 → 模式 FAULT
  → 占空比 **100%**（失效安全 = 满速，不是断电）
  → 继电器吸合 → **报警灯亮**
  → 蜂鸣器响（按过 K2 静音则不响，灯仍亮）
  → 只能靠 K2 长按复位；传感器没修好会立刻回到 FAULT
```

### 六、遥测帧与调参

`STREAM 1` 之后每 200 ms 一帧（全整数，**无 `%f`**，字段顺序是对外契约）：

```
@TEL,<seq>,<t_ms>,<mode>,<duty>,<temp_mc>,<adc>,<rpm>,<target_rpm>,<alarms>
@TEL,42,8200,3,48,31250,1980,5980,6000,0
```

`seq` 用于**检测丢帧**；`adc` 是**不受标定影响的原始量**，校准以它为准。

```bash
python tools/capture_serial.py --echo="STREAM 1" --seconds 30
python tools/plot_telemetry.py %TEMP%/smart_fan_serial_capture.txt
```

会抽出 CSV 并画一张四联图（温度 / **目标转速 vs 实测转速** / 占空比 / ADC）
—— 调 PI 主要看第二张。**这个工具是用来做系统辨识的**：
`docs/control.md` 里 τ ≈ 1.4 s 就是这么测出来的。

## 硬件


| 项 | 配置 |
|---|---|
| MCU | STM32F407VET6（LQFP100，512 KB Flash，128 KB RAM + 64 KB CCMRAM） |
| 主频 | 168 MHz（HSE 8 MHz 晶振 → PLLM=8 / PLLN=336 / PLLP=2） |
| 调试 | ST-Link，SWD（PA13 = SWDIO，PA14 = SWCLK） |
| 串口 | USART1，115200-8-N-1，**PA9 = TX / PA10 = RX**，接 CH340 USB 转串口 |
| OLED | SSD1306 128×64，**软件 I2C：PB6 = SCL / PB7 = SDA**，模块板载 4.7 kΩ 上拉 |
| 测温 | LM393 型 NTC 模块的 **AO → PA0（ADC1_IN0）**，模块 VCC 必须接 **3.3V** |
| 按键 | 两个轻触按键，另一端接 GND：**K1 = PC0 / K2 = PC1**，上拉输入，按下为低 |
| 风扇 | 12V 4 线 PWM 风扇：**PWM → PA8（TIM1_CH1，25 kHz，开漏）/ FG → PA1（TIM2_CH2 输入捕获）** |
| 继电器 | 高电平触发模块：**IN → PB0**，VCC 走**独立 5V**（线圈 ~70–90 mA 不占板子 3.3V 轨）。**接的是小灯，用作报警指示**——系统进 FAULT 时点亮 |
| 蜂鸣器 | 有源蜂鸣器模块，低电平触发：**IO → PB1**，VCC 接 3.3V |

CH340 与板子的接法（**必须交叉，且必须共地**）：

```
CH340 TX  ──►  PA10 (MCU RX)
CH340 RX  ◄──  PA9  (MCU TX)
CH340 GND ───  GND
```

完整的**引脚分配表、每个外设的接线图、以及电气上的硬性要求**
（NTC 模块为什么必须 3.3V、I2C 的上拉从哪来、ADC 采样时间为什么取 480 周期）
都在 [`docs/hardware.md`](docs/hardware.md)。

## 测试

`module/` 下的业务逻辑是**纯计算**（不含 HAL、不含寄存器、不碰寄存器地址），
所以能在**宿主机**上直接编译运行——不需要板子、不需要 ST-Link。
`tests/` 是一个**独立的 CMake 工程**（与固件的交叉编译工程隔离），
用 Unity 断言框架 + CTest 组织。

```bash
# 宿主机编译：用本机的 gcc，不走交叉工具链
cmake -S tests -B tests/build -G Ninja
cmake --build tests/build
ctest --test-dir tests/build --output-on-failure
```

| 测试目标 | 覆盖的内容 |
|---|---|
| `test_temperature` | NTC 分压反算、Beta 方程、端点与单调方向 |
| `test_fan_control` | FG 周期→转速（含毛刺/超时/边界）、档位步进、经验模型反解 |
| `test_fan_curve` | 分段插值、**迟滞不抖 / 该换挡时确实换**、边界钳位、非法配置 |
| `test_pi_control` | 抗积分饱和、限幅、限速率、无扰复位、**一阶对象闭环仿真收敛** |
| `test_thermal_control` | 级联闭环跟踪、占空比下限（不落未定义区）、兜底与恢复、dt 用真实时间 |
| `test_fan_fsm` | 各模式迁移、长按/短按、最小驻留、降级与 FAULT、外部报警透传 |
| `test_console` | 行协议解析、CRLF、超长行不越界、非法参数 |
| `test_telemetry` | CSV 帧**逐字节**匹配、负温度、缓冲不足报错 |
| `test_display_view` | **每行不超 21 字符**且内容完整（挡住越界静默绘制） |

CI（`.github/workflows/ci.yml`）有两个 job：宿主机单测、固件交叉编译。
前者拦住逻辑错，后者拦住构建/接口错。

## 验证

固件每 200 ms 输出一行遥测；上电时先做一次 I2C 总线扫描。
OLED 上同时显示（大字号温度 + 模式 + 目标/实测转速 + 报警）。

```bash
python tools/capture_serial.py                    # 复位板子并抓取
python tools/capture_serial.py --seconds 40       # 抓久一点
python tools/capture_serial.py --echo "PING"      # 发数据出去，验证 RX 回显
python tools/capture_serial.py --echo="STATUS"    # 打印一行完整状态
```

> ⚠️ 发以 `-` 开头的字符串要用 `--echo=...` 这种**等号**写法：
> 写成 `--echo "..."` 会被 argparse 当成选项，脚本直接报错退出。

预期输出：

```
==== smart_fan 智能温控风扇 ====
SYSCLK = 168000000 Hz
架构: app -> module(纯计算,可在 PC 单测) -> interface；bsp 贴硬件
温控: 温度 -> 分段曲线(+迟滞) -> 目标转速 -> 内环 PI -> PWM 占空比
...
I2C scan: 1 device(s) 0x3C
OLED: OK
[   466 ms] AUTO   T 23.8C  adc 2103  duty  30%  rpm 4800->5000  alarms 0x08
```

| 字段 | 含义 |
|---|---|
| `SYSCLK` | 时钟树对不对。**这行本身就是独立验证**：主频算错时串口波特率跟着错，整屏都是乱码，你根本读不到这行 |
| `I2C scan` / `OLED: OK` | 屏有没有应答、用了哪个地址 |
| 模式码 | `INIT` / `OFF` / `MANUAL` / `AUTO` / `DEGR` / `FAULT` |
| `T` | 换算出的温度。**未校准，只看趋势**；无效时显示 `---` |
| `adc` | ADC 原始计数（0~4095）。**这是没经过任何假设的数字**，校准以它为准 |
| `duty` | 当前占空比（%）。恒为 `0` 或 `≥20`——4 线风扇 <20% 行为未定义 |
| `rpm` | `实测 -> 目标`。**绝对倍率尚未用铭牌标定**（见下） |
| `alarms` | 报警位图（十六进制）：`01`=!TEMP `02`=!TACH `04`=!TRACK `08`=!CAL `10`=!OLED |

`alarms` 里 **`0x08`（!CAL）在 NTC 标定之前会一直亮着**——这是有意为之，
提醒看的人「温度这一维还没校准」。

> 命令表、按键表、报警位表、以及每种模式与故障场景的**具体现象**，
> 都在上面的「[功能与现象](#功能与现象)」一节，这里不重复。

### 上板验收清单

改完控制逻辑后，至少走一遍这五条。**「状态」一列是真实的**——
没跑过的就是没跑过，不要因为代码看起来对就当成过了（见下面的「验证纪律」）。

| # | 操作 | 预期 | 状态 |
|---|---|---|---|
| 1 | `MODE MANUAL` + `MANUAL 50` | 转速跟着命令走（实测 8480 rpm，与铭牌标定前的历史数据一致） | ✅ 已验证 |
| 2 | `MODE AUTO` + `TEMP 10`（把曲线左移，使目标落在可达区） | 闭环收敛：目标 5208 → 实测稳定在 5142~5282（±1.5%，即 1% 占空比的量化台阶） | ✅ 已验证 |
| 2b | AUTO 下**捏住 NTC 十几秒** | 转速随温度单调上升；松手后回落 | ⚠️ 部分验证：升温方向与迟滞行为已确认（26.1→29.5 ℃ 时目标正确换挡），但那时闭环还没整定好，未在稳定闭环下复测 |
| 3 | AUTO 下**拔掉 NTC** | 进 `DEGR`、出现 `!TEMP`、风扇维持安全转速（不停） | ❌ **未验证** |
| 4 | 同时拔掉 FG 线 | 进 `FAULT`：满速 + 报警灯亮 + 蜂鸣器响 | ❌ **未验证** |
| 5 | K2 长按 | 从 FAULT 复位回 AUTO（传感器没修好会立刻回到 FAULT——这是对的） | ❌ **未验证** |

#### 第 3~5 条未验证意味着什么

它们的**逻辑链条**已被单元测试覆盖（`test_thermal_control` 的兜底/恢复/丢信号用例、
`test_fan_fsm` 的降级/FAULT/复位用例），代码路径也逐段核对过。
但**单元测试证明不了硬件真的这么走**：真实的「拔掉 NTC 之后 AO 悬空读到什么值」
没人测过——STM32 的模拟输入悬空时的读数是不确定的，可能落在量程内，
那样 `temperature_from_adc_raw()` 不会返回错误码，兜底也就不会触发。

要结案必须上板做上面第 3~5 条。**在此之前，不要对外说这套失效保护「验证过」。**

### 排障：`I2C scan` 是第一入口

它能把三种原因一次分开：

- **一个地址都没有** → 接线 / 供电 / 上拉问题（`SCL`/`SDA` 接反也在这里暴露）；
- **只有 `0x3C`（或 `0x3D`）** → 正常；
- **出现别的地址** → 总线上挂了非预期器件。

串口链路的诊断看 `STATUS` 里的 `rx_drop` / `rx_err`：**接线松、没共地、
波特率不匹配时 `err` 会持续上涨**，比看现象猜接线快得多。

（若串口助手占着 COM 口，脚本会报 `FAILED_TO_OPEN` —— 先关掉它。）

### 风扇接线：三条实测踩过的坑

1. **必须共地。** 风扇的 12V 电源负极要和板子 GND 接在一起。不共地时 PA8 的
   低电平对风扇而言没有参考点，现象是「占空比怎么调风扇都全速转」，
   和「线没接对」一模一样。**上电顺序也固定：先让板子跑起来，再给风扇 12V**——
   反过来 PWM 引脚还是浮空输入，风扇内部上拉直接把它顶到 100%。
2. **线色不可信，以实测为准。** 本项目就撞上了：按常规配色接的 PWM/FG
   两根线实际是反的（PA8 上挂的其实是测速线），结果风扇无视占空比、`fg` 恒为 0。
   判定方法见下面「怎么认哪根是 PWM」。
3. **低于 20% 的占空比行为未定义。** 4 线风扇规范写明 20% 以下由厂商自定，
   本工程实测 0% 时风扇维持约 295 rpm 而不是停转。**要真停只能切 12V。**

#### 怎么认哪根是 PWM（不用万用表）

保持 12V 供电，把疑似 PWM 的那根线从板子上拔掉：

- 风扇**立刻回到全速** → 它确实是 PWM 控制线（拔掉后输入悬空，内部上拉把它顶到 100%）；
- 风扇**毫无变化** → 那是测速线。

> **诊断入口目前没有接到串口上。** `bsp/bsp_fan.h` 里的
> `bsp_fan_force_pin_low()` 仍然在——它绕过定时器把 PA8 / PA1 直接拉低，
> 用来把「引脚没被拉低」和「线没接到这个脚上」两件事分开
> （**执行后需复位板子才能恢复**）。但改成温控应用之后，原先测试台里那三个
> 单字符诊断命令（`8` / `1` / `p`）被一并删掉了。
> 要恢复它们，在 `app/app_console.c` 里加一条命令接到这个函数即可（约十行）。
> 之所以没有默认保留：它会让引脚停在一个非正常状态、必须复位才能继续，
> 放在日常可用的控制台里是个陷阱。

#### RPM 绝对倍率待标定

`rpm` 的换算基于两个假设：FG **每转 2 个脉冲**（Intel 规范值）、且**每个边沿只被
捕获一次**。实测 100% 时读到约 16400 rpm，线性度很好，但绝对值还没和铭牌对过。

> **这一条不影响控温的正确性**：曲线的纵轴与内环用的是同一个「观测转速」，
> 倍率误差在闭环内被消掉，只影响屏上数字的物理含义。
> 标定后把曲线纵轴与经验模型常数**按同一倍率**一起缩放即可。
> 详见 [`docs/control.md`](docs/control.md) 的「待标定」。
若与风扇铭牌差一个固定倍数，两个可能：**每转脉冲数不是 2**（改
`FAN_CONTROL_PULSES_PER_REV`），或 **FG 边沿有振铃被重复捕获**——后者目前只用
STM32 内部约 40 kΩ 上拉、且未开输入滤波器，修法是开 TIM2 的输入捕获数字滤波器，
并在 PA1 与 3V3 之间加一只 4.7 kΩ 外部上拉。

## 改配置（时钟 / 外设）

**外设、引脚、时钟树一律通过 CubeMX 改，不要手写 `.ioc`。**

`.ioc` 是 CubeMX 内部状态的序列化：手写 `Mcu.IPn=TIM1` 这类「该外设已激活」的**记录**，
CubeMX 重建不出对应状态就整块**静默丢弃**——不报错、不警告，参数连同记录一起没了。

所以本工程把配置改动都写成 [`cube-recipes/`](cube-recipes/) 下的配方文件，
用仓库自带的 `tools/cubemx_apply.py` 喂给 CubeMX 自己的脚本模式：

```bash
python tools/cubemx_apply.py apply      . "cube-recipes/r1-hse-usart-swd.txt"
python tools/cubemx_apply.py apply      . "cube-recipes/r2-时钟树.txt"   # 必须在 r1 之后
python tools/cubemx_apply.py apply      . "cube-recipes/r3-oled-ntc-key.txt"
python tools/cubemx_apply.py roundtrip  .                               # 验证改动被接受
python tools/cubemx_apply.py regenerate .                               # 生成代码
```

`apply` **只改 `.ioc`，不生成代码**。要出代码必须再跑一次生成：

```bash
python tools/cubemx_apply.py regenerate .
```

它会先给 `Core/` 下所有 `USER CODE` 块拍快照，生成后再逐块比对——
**丢了或改了就返回非 0**，并把生成前的副本路径打出来。
（CubeMX 靠「读回这些块」保留用户代码，而这个机制**偶尔静默失效**：
块被整段清空、返回码还是 0、一句报错都没有。详见
[`docs/walkthrough.md`](docs/walkthrough.md) 阶段 5。）

> ⚠️ **别拿返回码判断生成成没成功。** 实测 `project path` 这条在脚本模式下会回 `KO`，
> 而生成完全正常。`regenerate` 因此比对的是 `Core/` 下文件的**内容**——
> 也不用 mtime：CubeMX 在生成结果与磁盘上已有内容一致时**不重写文件**，
> mtime 不变，拿它判「有没有生成」会误报。

> ⚠️ **时钟树必须分两遍跑**，原因写在 [`cube-recipes/r2-时钟树.txt`](cube-recipes/r2-时钟树.txt)
> 顶部：`RCC.HSE_VALUE` 只在 CubeMX `config load` 那一刻被时钟模型读取，写在同一遍里
> 会导致「命令全 OK、键也落盘、roundtrip 也报原样保留，但主频算错」。

改完配置的验收要分四层做，缺一层就会出现「全绿但错」——
见 [`docs/architecture.md`](docs/architecture.md) 的「验证纪律」。

## 目录结构

```
smart_fan/
├── Core/            CubeMX 生成：HAL 适配、main.c、中断向量
├── Drivers/         CubeMX 生成：HAL 驱动 + CMSIS
├── cmake/           CubeMX 生成：CMake 胶水
├── interface/       硬件抽象契约（只有声明，无实现、无厂商头文件）
├── driver/          驱动
│   ├── bus/         总线实现（软件 I2C）——贴 HAL 的那一层
│   └── device/      器件驱动（SSD1306）——纯可移植，不含任何 STM32 符号
├── bsp/             板级绑定：把契约与驱动绑到具体引脚/外设
├── module/          业务逻辑（纯计算，可在 PC 上单测）
│   ├── common/        共享值类型（采样、模式、报警位）
│   ├── temperature/   ADC 计数 → 毫摄氏度
│   ├── fan_control/   FG 周期 → 转速、档位步进、转速↔占空比经验模型
│   ├── fan_curve/     温度 → 目标转速（分段插值 + 迟滞）
│   ├── pi_control/    通用 PI（抗饱和 / 限幅 / 限速率）
│   ├── thermal_control/ 级联控制器（上面三者的组合）
│   ├── fan_fsm/       运行模式状态机
│   ├── console/       串口行命令解析
│   ├── telemetry/     遥测帧格式化
│   └── display_view/  OLED 视图模型（约束行宽）
├── app/             启动编排、时间触发调度器、控制编排、串口、显示
├── tests/           宿主机单元测试（独立 CMake 工程 + Unity）
├── cube-recipes/    下达给 CubeMX 的配置配方（改配置的唯一入口）
├── docs/            架构说明 + 控制文档 + 完整开发过程记录
├── tools/           cubemx_apply.py（配置下达）、capture_serial.py（串口抓取）、
│                    plot_telemetry.py（遥测抽取与绘图）
├── .github/         CI：宿主机单测 + 固件交叉编译
└── .vscode/         clangd / CMake Tools / 断点调试配置
```

**VSCode 打开的就是这一层目录本身**，不要用外层目录当工作区——
ST 的工具链假设「工作区根 == CMake 工程目录」，错开会让它
从代码索引到调试以三种不同面目失败。

分层与依赖方向（`APP → MODULE → INTERFACE`，`BSP → DRIVER → PLATFORM`，
以及 `module/` 内部那条唯一的组合依赖），
还有「为什么把厂商代码留在 `Core/`+`Drivers/` 而不是搬进 `platform/`」，
都写在 [`docs/architecture.md`](docs/architecture.md)。
