# driver/ — 驱动层

这里放**与具体器件/总线打交道**的代码，分成两类：

```
driver/
├── bus/        总线驱动：把「怎么发一个字节」这件事做到引脚上
│   └── i2c/    软件模拟（位翻转）I2C
└── device/     器件驱动：把「某个芯片的寄存器怎么用」封装成函数
    └── ssd1306/  128×64 单色 OLED
```

再往上一层是 [`bsp/`](../bsp)：它回答「**这块板子上**，屏挂在哪条总线、
按键接在哪两个脚」。同一份 `device/` 驱动配不同 `bsp/` 就能用在别的板子上。

## 硬性约束

### `device/` 里的代码不许出现任何 STM32 符号

- **禁止**：`HAL_*`、`GPIO_TypeDef`、`I2C_HandleTypeDef`、寄存器名、CMSIS、
  以及任何引脚号。
- 要用硬件能力，**只通过 [`interface/`](../interface) 的契约**
  （如 `i2c_if_t` 的三个函数指针）。
- 需要延时？由上层**注入一个函数指针**，不要在驱动里直接调 `HAL_Delay`。

理由不是洁癖：`ssd1306.c` 现在换到 GD32 / ESP32 / 树莓派上**一行都不用改**，
只要目标平台提供一份实现了 `i2c_if_t` 的总线。一旦它里面出现 `HAL_I2C_*`，
这个性质立刻消失。

附带的好处是**可以在 PC 上测**：给一份「把收到的字节打印出来」的假总线
（几十行），就能不接硬件验证显存组织、字模绘制、坐标越界这些纯逻辑——
它们在硬件上调试一次的成本远高于写一个假实现。

### `bus/` 是唯一允许贴着 HAL 的驱动

`i2c_soft.c` 直接用 `HAL_GPIO_*`，这是它的职责。但它**不许**包含具体器件的协议
（SSD1306 的命令字之类）——那是 `device/` 的事。

引脚**不写死在总线驱动里**：由 `bsp/` 通过
[`i2c_soft_cfg_t`](bus/i2c/i2c_soft.h) 注入，所以同一份实现能驱动任意两根 GPIO。

## 边界感：一个例子

`bsp/bsp_oled.c` 里的总线探测，只用 `i2c_if_t::write` 发一个控制字节看有没有 ACK。
它不需要知道 SSD1306 的内部结构，只需要「总线上这个地址有没有人应答」。
反过来，`ssd1306.c` 也不知道自己挂在 PB6/PB7 还是别的什么地方。

## 命名

- 类型：`typename_t`（如 `i2c_soft_t`、`ssd1306_t`）
- 函数：`前缀_动作()`（如 `i2c_soft_init()`、`ssd1306_write_string()`）
- 宏：`前缀_描述`（如 `I2C_SOFT_DEFAULT_FREQ_HZ`、`SSD1306_WIDTH`）
- 文件内函数一律 `static`——驱动状态挂在实例结构体上，**不用全局变量**，
  于是同一条总线上可以并存多块屏，也便于测试

## 加一个新器件驱动时

1. 目录 `driver/device/<器件名>/`，至少 `<器件名>.c` + `<器件名>.h`；
   大器件可以把寄存器定义单独拆一个 `_reg.h`（参考 `ssd1306_reg.h`）。
2. `.h` 只 include `interface/` 的契约和标准库。
3. 状态全放实例结构体，初始化函数由调用者传实例进来。
4. 所有对外函数返回 `error_t`，禁止用裸 `-1` / `0` 表达失败。
5. 在 `CMakeLists.txt` 的 `target_sources` 里加上 `.c`。
6. 在 `bsp/` 里写绑定的那一层（哪条总线、哪个地址、延时怎么给）。
